# WS1 notes — database, models, internal admin

Scope: ARCHITECTURE.md sections B, J, K.1. Everything in section B is implemented (18 tables, 18 models +
`Current`, the audit concern, 7 dashboards, 7 admin controllers, the JSON field, seed migration, tests).

## Deviations from ARCHITECTURE.md

**Names: none.** Table names, column names, types, defaults, index columns, class names, file paths,
constants and the method names listed in K.1 match the document.

Three non-naming points the integrator should know about:

1. **`db/schema.rb` was NOT edited** (K.1 lists it under "Edits"). Per the WS1 brief it must be
   regenerated by `rails db:migrate` on a real environment, not hand-written. Until that is done, the
   test database (loaded from `schema.rb`) has none of the new tables and `test/models/cod_form/*` fail.
2. **Seed data is written inline in `20261003101900_seed_cod_form_defaults.rb`**, not read from
   `CodForm::Engine::Defaults.feature_gates` / `.plan_limits`, so the migration has no dependency on app
   code (it uses migration-local model classes and no callbacks). The values are those of J.1 / J.2
   (identical to PM_DECISIONS Q8 / Q9). If WS2's `Defaults` ever differs, the document's tables win.
3. **One extra file in an owned directory:** `app/controllers/admin/cod_form/admin_context.rb`
   (`Admin::CodForm::AdminContext`, a concern). The seven controllers still inherit
   `Admin::ApplicationController` directly, as J.3 says; the concern holds the shared `before_action`
   that sets `::CodForm::Current.actor` / `.ip` and the JSON-text parsing for `JsonTextField`.

## Assumptions (ambiguities resolved)

1. **`Form.default_for` creates the default form already published** (`published_version: 1`,
   `draft_config = published_config = CodForm::Engine::Defaults.form_config`). The storefront reads only
   `published_config`; an unpublished default form would make every first session fail with `config_error`.
2. **`Form#publish!` raises on engine errors** (`ActiveRecord::RecordInvalid`) rather than returning false,
   following the bang convention. The admin API (WS6) should rescue it or call `FormConfig.normalize` first.
3. **`OrderUsage.for` does not create a row** (see table above).
4. **`ShopConfig#module_enabled?` excludes the kill switch**, because F.1 gives `CodForm::Availability`
   the kill-switch check separately.
5. **`enabled_at`** is stamped by the model the first time a row is saved with `storefront_mode = "cod_form"`
   and never cleared.
6. **A/B variants become immutable** from the moment `started_at` is set, also after the test is stopped.
7. **Block-entry format checks:** phone 5–15 digits after normalisation; email `local@domain.tld` or
   `*@domain.tld`; ip anything `IPAddr.new` accepts (IPv4, IPv6, CIDR).
8. **`PlanLimit.plan_tier` is refused on `plan` and `shop` rows** (B.12: "only for `country_group` rows").
9. **Country-group seed lookup is by name** ("Launch markets"). If the group is renamed in the admin before
   the seed migration is re-run on that database, a second group would be created; the migration runs once
   per database, so this only matters for a manual re-run.
10. **`AdminAudited` on `ShopConfig`** skips create and destroy (rows are created lazily by merchant
    traffic, which is not an admin action).

## Open issues

- **Gate / cap edits do not re-sync shop metafields.** Editing a `feature_gates`, `plan_limits` or
  `cod_form_country_groups` row in the admin changes what `features` / `cap_fallback` / `enabled` should be
  in shop metafields, but only global-setting and shop-config edits trigger a re-sync today. The server
  still enforces gates and caps at session and submit, so the effect is a stale storefront hint until the
  shop's next config write. Product/WS6 should decide whether those three admin controllers should also
  enqueue `MetafieldSyncAllJob`.
- **`GlobalSetting.current` is cached for 30 s per process cache store**; with a non-shared cache store
  (memory store) other processes see a kill-switch flip up to 30 s late. Production uses a shared store
  if `Rails.cache` is Redis-backed (the document assumes so in D.0.4).
- **`tracking_pixels.access_token` and `cod_form_integrations.credentials` are stored in plain text**, as
  B.10 specifies ("stored like `settings.pixel_token` today").
- Administrate's handling of the namespaced resources (sidebar labels, `Field::Select` `include_blank`)
  was written against administrate 0.20.1 from the gem's documented behaviour and could not be clicked
  through here.
